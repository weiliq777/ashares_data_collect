# 数据基座架构拆分方案

> 目标：把当前 `ashares_data_collect`（数据基座 + 策略 + 回测 + 决策 + 组合 + 新闻 + 微观结构
> 混在一起）重构为**纯粹的数据基座（Data Foundation）**，应用层与基座彻底分离，各自独立演进。
>
> 更新日期：2026-08-16（基于当前代码库现状，所有越界点均有代码实证）
>
> **状态：Architecture Baseline v1.0（架构已冻结）** —— 主干层级（Raw → Versioned Fact → Standard →
> PIT → Feature → Mart → Daily Snapshot / Dataset Release → Research Application）不再轻易改动；
> 后续问题优先通过「新增版本 / 新增契约 / 新增数据域」解决，而非推翻主干。
> 下一阶段按 §7 从 Stage 1 开始落地执行。

## 1. 现状盘点：混在哪里

### 1.1 当前 Schema 地图

| Schema | 内容 | 归属（现状） | 归属（目标） |
|---|---|---|---|
| `public` | **Raw 原始表**（`tushare_market_raw_version`、`tushare_*_raw_version`…）、**Standard**（`daily_kline`、`stock_basic_info`、`adj_factor_daily`…）、**指数/基准事实**（`index_daily`、`index_minute`、`index_weight`…）、以及**业务旁路表**（`limit_pool`、`margin_daily`、`block_trade`、`fund_flow_daily`、`etf_*`、`instrument_info`、`wave3_stocks`…） | 混杂区 | **基座**（Raw/Standard/指数基准保留，归入 std/pit；业务旁路表按领域拆分或迁移） |
| `std` / `pit` / `feature` / `ops` | 阶段二标准层、时点层、特征层、运维事实（018 创建） | 基座雏形 | **基座** |
| `research` | 冻结快照、观察池、候选、AI 审计、人工决策（024/026/027/034/045/046） | 契约接口 + 应用混合 | **契约接口区**（快照）+ **应用区**（候选/审计/决策）分开 |
| `backtest` | 数据集、运行、规则、订单、事件账本（028/030~044） | 应用 | **应用** |
| `portfolio` | 纸面组合（029/032） | 应用 | **应用** |

### 1.2 越界点清单（必须整改）

| # | 越界行为 | 位置（实证） | 问题 |
|---|---|---|---|
| 1 | **应用绕过特征层，自己算指标** | `jobs/wave3.py` 直接读 `daily_kline` + 自己调 talib 算 WR/RSI/KDJ，复权因子自己拼 | 同一指标两套算法；特征层不可信 |
| 2 | **策略参数写进"已批准事实规则"表** | `engine.py:230` 把 ROE>15、增速>30% 硬编码并冻结；`backtest_rules.py` 审批只验格式不验效果 | 研究假设伪装成数据事实；换策略要动"规则治理" |
| 3 | **执行域配置混入规则治理** | `backtest_rules_approved_v3.yaml` 的佣金/印花税/滑点/跳空/成交量参与率与市场规则同表 `backtest.market_rule_effective` | 交易费用是执行假设，不是数据事实；应随策略版本管理 |
| 4 | **候选生成直读基座派生表** | `candidate_service.py:get_stock_history` 读 `feature.price_daily_v2`（虽标注"仅供探索"，但仍在同一进程内可触达） | 契约未隔离，容易在后续改动中变成正式输入 |
| 5 | **快照字段被单一策略绑架** | `research.stock_snapshot_daily` 同时存通用研究字段（ma/pe/roe）与**为 v2 策略定制的双轨字段**（`roe_5y_all_above_15`、`q_sales_yoy_4q_all_above_30`…） | 换策略就要改快照结构；快照应是"通用可研究字段全集" |
| 6 | **同一仓库承载多个无关领域** | news 子系统、tick-microstructure skill、qmt-xtquant skill、etf/期权/打板采集 | 数据基座仓库被无关领域拖累 CI/部署/权限 |

### 1.3 结论

Raw→Standard→PIT→Feature 的骨架是**好的**（天然 Medallion），不需要推倒。
**缺的是边界纪律**：谁可以读、谁可以写、什么算事实、什么算假设、应用从哪取数。

### 2.2 基座层职责定义（判定标准：这层只回答一个问题）

| 层 | 回答的问题 | 写入者 | 读取者 |
|---|---|---|---|
| Raw | 数据源返回了什么？（原样、不可变、带溯源哈希） | 采集任务（只追加） | 仅标准层/重建任务 |
| Versioned Fact | 同一事实有哪些版本？哪个版本何时可见？（`version_available_date`，财务数据尤其关键） | 标准层任务 | PIT |
| Standard | 数据统一形态？（schema/单位/代码归一） | 标准层任务 | PIT/Feature |
| PIT | 某一天"当时能看到什么"？（时点可见性） | PIT 任务 | Feature/快照 |
| Feature | 指标算出来是多少？（MA/量比/PE分位/ROE…） | 特征任务（可重建） | 快照/应用视图 |
| Mart/契约 | 给应用的最方便形态？（冻结快照/宽表/视图） | 发布任务 | **应用访问基座的唯一边界** |
| ops | 数据覆盖/质量/重建进度的事实记录 | 各任务 | 监控/门禁 |

**铁律：基座内部不出现"策略、买卖、回测、止损"任何概念。** 基座负责把 ROE 算对、算准、
可追溯、可重建——"ROE>15 才值得买"这句话，基座永远不该知道。

### 2.4 澄清：两个不同层次的 Universe（避免命名混淆）

架构图里 `Universe` 出现在应用层顶端，而 §2.2 的 `pit.universe_daily` 在基座 PIT 层——
两者**不是同一个概念**，必须分开：

| 概念 | 所在层 | 含义 |
|---|---|---|
| **物理标的池** `pit.universe_daily` | 基座 PIT | 客观物理事实：某日全市场有哪些股票上市交易、退市、ST、停牌（数据事实，不含任何策略判断） |
| **策略标的池** `app_strategy_universe` | 应用 | 策略在物理标的池上二次过滤的结果（如"仅沪深300成分"、"剔除上市未满1年"、"市值前500"） |

原则：**基座只产出物理标的池；"选哪些股票来研究"是应用层的策略决定。**

### 2.5 PIT 三时间语义（防未来函数的关键）

Versioned Fact 的时点可见性不能只靠一个 `version_available_date`，一个事实至少有三个时间，**不能混**：

| 时间 | 含义 | 示例（茅台 2025 年报） |
|---|---|---|
| **business/effective time 业务时间** | 数据描述什么时候 | `report_period = 2025-12-31` |
| **available time 可见时间** | 市场什么时候真正能知道 | `available_at = 2026-03-28 19:32` |
| **ingestion time 入库时间** | 你的系统什么时候拿到 | `ingested_at = 2026-03-29 02:10` |

**治理陷阱**：Tushare 补历史修正数据时，源数据 `ann_date=2024-03-20` 可能你 `2026-08-16` 才第一次抓到。
此时必须保存两个：`source_available_at`（源数据公告日）与 `first_seen_at`（系统首次发现日），
并在 PIT 规则中**显式声明用哪个**（建议统一用 `version_available_date` 的可见口径，禁止混用
`source_available_at` 与 `first_seen_at`）。这对"防未来函数"系统是长期必须厘清的。

## 3. 目标 Schema 划分（PostgreSQL 落地）

### 3.1 基座 schema（data-foundation 仓库独占）

```
raw_*        （新建 schema，迁移现有 public.tushare_*_raw_version）
             └─ 每行：source_record_key / record_version / payload_hash / fetched_at
std          （已有）统一标准表；财务/制度类保留 version_available_date + record_version
             （即 Versioned Fact 载体，见 §2.2）
pit          （已有）时点表
feature      （已有）特征表；新增 feature.feature_registry（见 §3.4）
ops          （已有）质量/覆盖率/检查点事实表；新增 ops.source_registry / ops.change_event（见 §3.4）
mart         （新建）应用只读视图 v_*（宽表投影，禁止直接读 feature/pit）
foundation.rule_*（新建）市场客观事实与历史真实**制度**（制度定义）：
             - market_rule_effective（整手 / T+1 / 价格档位 / 涨跌幅区间）
             - tax_rule_effective（印花税等历史真实税率，按日期版本生效）
             - settlement_rule_effective（结算 / T+N 资金可用）
foundation.price_limit_daily（新建）每日实际涨跌停价**事实表**（up_limit/down_limit，来自 Tushare stk_limit）
             （注意区分：`price_limit_daily` 是"每日实际涨跌停价"的事实；"创业板 20% / 主板 10% / ST 5%"
               这种制度定义才叫 rule，两者长期必须分开）
```

> **物理分区（Table Partitioning）**：`contract.stock_snapshot_daily`、`feature.*` 等按
> `trade_date` 增长的大表，按年（或按月）做 PostgreSQL 声明式分区；分区键一律用
> `trade_date`，避免全表扫描与 `VACUUM`/索引重建的维护成本随行数线性恶化（现有 agent.md
> 已记录过 16GB 大表全表统计导致宿主机失去响应的教训）。

### 3.2 契约接口区（数据产品，由基座发布、应用消费，**独立 `contract` schema**）

> 契约区必须独立成 `contract` schema，不能与应用的 `research.*`（候选/审计/决策）混在同一
> schema——否则拆 `data-foundation` / `research-app` 两仓库时 ownership 冲突（谁拥有、谁能写）。

```
contract.snapshot_manifest          — 快照元数据（FROZEN 状态机）
contract.stock_snapshot_daily       — 通用研究字段冻结快照（字段集见 §5.2 去策略化）
contract.data_dictionary            — （新建）字段字典：列名 ↔ 中文业务含义 ↔ 计算口径 ↔ 来源
contract.contract_version           — （新建）契约版本号，应用锁定版本消费
contract.dataset_release            — （新建）回测数据集发布物（FROZEN Backtest Dataset，见 §4.8）
```

### 3.3 应用 schema（research-app 仓库独占）

> `research` schema 只保留**应用侧**对象（候选/审计/决策/观察池）；快照等基座契约对象已迁入
> `contract` schema（见 §3.2），两者 ownership 严格分离。

```
research.candidate_run / candidate / ai_audit / human_decision / evidence_reference
research.watchlist / watchlist_member
backtest.*    （dataset/run/order/fill/event ledger；市场规则/税则读取基座 foundation.rule_*）
portfolio.*
app_strategy_version   （新建）策略参数版本表：策略ID/版本/阈值JSON/审批/回测证据哈希
app_execution_params   （新建）执行假设参数表：佣金/滑点/跳空/成交量参与率/成交模型，按版本生效
                       （印花税等历史真实税则不进这里，读基座 foundation.tax_rule_effective）
```

> **拆分要点**：把现在混在 `backtest.market_rule_effective` 里的三类东西拆开——
> ① 市场客观事实（涨跌停价、整手、T+1、价格档位）→ 基座 `foundation.market_rule_effective` / `price_limit_daily`（事实表）；
> ② 历史真实制度（印花税税率按日期变化）→ 基座 `foundation.tax_rule_effective` / `settlement_rule_effective`；
> ③ 执行假设（佣金、滑点、跳空、成交量参与率、成交模型）→ 应用 `app_execution_params`。
> 判断标准：**这个数字会不会因为"换了券商 / 改了策略 / 换了撮合模型"而变化？会 → 应用；不会（交易所/国家规定的客观事实）→ 基座。**

### 3.4 元数据与注册表（Registry）—— 长期运行的"字典与影响分析"

#### 3.4.1 Feature Registry（`feature.feature_registry`）

Feature 增多后必须有注册表，避免 `roe / roe_v2 / roe_ttm / roe_new / roe_fixed` 混乱。每条记录：

```
feature_name / feature_version / business_name / definition /
source_datasets / dependency_features /
lookback_rule / asof_rule / adjustment_rule /
impact_rule / quality_rule / code_version / status / created_at
```

**核心作用**：`impact_rule` 回答"新数据来了，哪些 Feature 要重算？"
（例：`pe_pct_5y` 的 impact_rule = "历史 PE 修正后，重建该股票自修正日起后续 5 年窗口"）。

#### 3.4.2 Source Registry（`ops.source_registry`）

未来不止 Tushare（QMT/东财/同花顺/新浪）。每个数据源注册：

```
source_id / provider / api_name / dataset_name / business_key / frequency /
supports_incremental / supports_backfill / available_time_rule / rate_limit / enabled
```

**核心作用**：新增数据源 = 注册 → Raw Adapter → Standard Mapping → PIT → Feature，
而非散落写新的 Python Job（现有 `utils/source_registry.py` 已是雏形，扩展为完整注册表）。

#### 3.4.3 Change Event + Impact Resolver（`ops.change_event`）

Dataset Ready 回答"今天数据是否就绪"，但还缺"**昨天历史数据被修正后该重建什么**"。记录：

```
event_id / dataset / business_key / ts_code / effective_date /
old_hash / new_hash / source_run_id / detected_at / change_type / status
```

流程：

```text
Change Event（如 financial_income / 600519.SH / 2025-12-31 / hash 变化）
      ↓
Impact Resolver（解析影响范围）
      ↓
只重建受影响的 Standard → PIT → Feature → Snapshot（而非全量重跑）
```

## 4. 接口契约定义（应用的两类取数通道）

应用取数分两类通道，各有明确用途，**不要绝对化"只能读 Snapshot"**：

| 通道 | 用途 | 数据形态 |
|---|---|---|
| 冻结快照 | **每日研究 / 选股**（必须可复现、可审计） | `contract.stock_snapshot_daily`（FROZEN） |
| 回测数据集 | **正式五年回测**（历史区间，非单日截面） | `contract.dataset_release`（FROZEN，见 §4.8） |
| 只读视图 | **探索 / 调试 / 画图 / 排查指标**（允许看最新值） | `mart.v_*` |

### 4.1 契约一：冻结快照（每日研究/选股的**唯一**入口）

```sql
-- 每日研究/选股只准走这里：一个 FROZEN snapshot 即一个交易日的只读全市场截面
SELECT * FROM contract.stock_snapshot_daily
 WHERE snapshot_id = :snapshot_id AND research_date = :trade_date;
```

契约规则：
- 应用只能读 `status='FROZEN'` 的快照；DRAFT/VALIDATED 一律不可见（现有触发器已支持）
- 快照字段集由基座契约版本管理；应用升级必须显式声明 `contract_version`
- 快照含 `input_manifest_hash` / `quality_report_hash`，应用可校验数据未被污染

### 4.2 契约二：只读视图（探索/调试入口，按需宽表）

```sql
CREATE VIEW mart.v_price_feature AS
SELECT p.ts_code, p.trade_date, p.raw_close, p.asof_close, p.ma20, p.ma60, p.ma120,
       p.volume_ratio_20d, p.volatility_20d, v.pe_ttm, v.pe_pct_5y, v.pb_pct_5y
  FROM feature.price_daily_v2 p
  LEFT JOIN feature.valuation_daily_v1 v USING (ts_code, trade_date);
```

规则：应用**只准读 `mart.v_*`**，基座内部表 `feature.*`/`pit.*`/`std.*` 对应用只读授权
但不在文档/字典中承诺（内部实现可随时迁移）。

### 4.3 契约三：数据字典与字段口径（防"看不懂"的第一道防线）

`contract.data_dictionary` 每行记录：

| 列 | 说明 |
|---|---|
| table_name / column_name | 表.列 |
| business_name | 中文业务名（如 "20日均线"） |
| definition | 计算口径（"最近20个交易日复权收盘价均值"） |
| source | 来源（Tushare接口 / 派生计算 / 人工定义） |
| quality_rule | 质量规则（非空/范围/单位/交叉验证） |
| contract_version | 所属契约版本 |

> 现有 `agent.md` 已要求"说明表名时必须附带业务含义"——把这条纪律固化成表。

### 4.4 契约四：查询 API（可选，非必需）

若未来有 Web/多端需求，基座可暴露只读 HTTP API（`/snapshots/{id}`、`/candles/{code}`），
内部仍是冻结快照 + 视图。第一版不强求，SQL 视图足够。

### 4.5 契约五：交易日出构建状态机（Dataset Ready，**核心能力**）

> "某交易日数据是否就绪"必须是核心能力，不能靠"可选增强"。每天都要明确知道某日处于
> `READY / PARTIAL / FAILED / STALE / BUILDING` 哪种状态。通知机制（LISTEN/NOTIFY/Webhook）可以
> 可选，但**就绪状态本身必须结构化**。

建议 `ops.trading_day_build` 表：

```text
trade_date
pipeline_version
raw_status / standard_status / pit_status / feature_status / quality_status / snapshot_status
started_at / completed_at / error_code / retry_count
final_status   -- READY / PARTIAL / FAILED / STALE / BUILDING
```

`final_status = READY` 才允许 `Snapshot → FROZEN`、`Dataset → FROZEN`。应用据此轮询/订阅触发选股与回测。
（通知机制可选：`LISTEN/NOTIFY`、Webhook、应用轮询均可，只是通信方式不同。）

### 4.6 契约六：向量化导出通道 Parquet（可选增强）

基座冻结 Snapshot 时，可同步导出一份按交易日/年份组织的 `.parquet` 只读文件到存储卷；
研究应用（Python/Polars/DuckDB）直接加载 Parquet 做向量化计算，吞吐比逐行 SQL 提升 10~100 倍。
（项目已有 Tick 按日 Parquet 冷存的先例，此通道只是把同样机制延伸到快照/宽表。）

### 4.7 复权治理规范（明确除权息时点契约）

量化基座最易出错的算术是复权价格。当前项目已用**时点总收益复权（asof）**，治理规范据此写：

| 要点 | 规范 |
|---|---|
| Standard 层持久化 | 存**真实不复权 K 线**（`daily_kline.raw_close`）+ **复权事实表**（除权息事件 `std.dividend_event`） |
| Feature 层口径 | `price_daily_v2.asof_close` 采用**时点总收益复权**（只在除权日回放已实施事件，见 `tushare_phase2_features.py:172`） |
| ⚠️ 禁止做法 | **不得用 `adj_factor_daily` 做"前复权"（`raw_close * adj_factor`）** —— 该值是最终仓库值、无公告时点，会导致前视偏差；v2 已明确弃用（代码注释 `does not carry an announcement vintage. v2 therefore does not use it`） |
| 快照不变性 | 已 FROZEN 快照固定当时的 asof 截面；历史除权息修正 → 发布新版本快照（`RS_v2`），**禁止原地 UPDATE** |

> 注：评审建议的"mart 统一暴露前复权口径 `raw_close * adj_factor`"**不采纳**——那正是 v1 已弃用的前视偏差做法，正确口径是 asof 总收益复权。

### 4.8 契约七：回测数据集（FROZEN Backtest Dataset / Dataset Release，正式回测的入口）

每日选股用 Snapshot（单日截面），但**五年回测需要的是"一段历史区间的完整冻结研究世界"**，两者是不同的数据对象，必须并列：

| 对象 | 粒度 | 用途 |
|---|---|---|
| `contract.stock_snapshot_daily`（FROZEN Snapshot） | 单日截面 | 每日研究 / 选股 |
| `contract.dataset_release`（FROZEN Backtest Dataset） | 历史区间（如 2021-08-01 ~ 2026-08-01） | 正式回测 |

`dataset_release` 记录：`dataset_id / start_date / end_date / 包含哪些交易日 / 使用的 Snapshot 集合 /
feature_version / pit_version / data_baseline / contract_version / manifest_hash / status=FROZEN`。

**关键**：执行规则、手续费、滑点**不塞进 Dataset**，它们绑定到 `Backtest Run`：

```text
FROZEN Backtest Dataset
        + Strategy Version（策略参数）
        + Execution Params Version（佣金/滑点/成交模型）
        + Market Rule Version（市场客观规则）
        ↓
    Backtest Run（可复现）
```

这样 `Strategy V2 + Execution V1` 与 `Strategy V3 + Execution V2` 可复用**同一个 Dataset**，策略归因才干净。

## 6. 治理规则（基座的"宪法"）

1. **不可变**：Raw 只追加；任何修复=新增版本记录，不 UPDATE/DELETE（现有触发器已部分实现，扩到全部 Raw 表）
2. **分层幂等**（"幂等"是目标，不是 `ON CONFLICT DO NOTHING` 一个写法）：
   - **Raw**：Append Only；同 payload_hash → `DO NOTHING`；源数据修订（business key 同、hash 不同）→ `INSERT` 新版本
   - **Versioned Fact**：新版本 `INSERT`，历史版本不覆盖
   - **Standard / PIT / Feature**：可重建；增量 → `ON CONFLICT DO UPDATE`（upsert）；批量 → staging + publish
   - **FROZEN Snapshot / Dataset**：绝对禁止 UPDATE；数据变化 → 新 snapshot_version / dataset_version
3. **版本化**：快照/数据集/规则全部带版本与哈希，改动必须新增版本（现有已实现，保持）
4. **权限隔离**：
   - 应用账号：只读 `contract.*`（FROZEN）+ `mart.v_*`；应用可写自己的 `research.*`/`backtest.*`/`portfolio.*`
   - 基座账号：只写 `raw/std/pit/feature/mart/ops/foundation/contract`；不得读写应用侧 `research`/`backtest`/`portfolio`
5. **Data Quality Contract（六类检查）**：快照/Dataset FROZEN 前必须通过，规则带 `severity: INFO/WARN/BLOCK`，仅 `BLOCK=0` 才允许 FROZEN：
   - **Completeness 完整性**（如交易日应 5400 只、实际 3900 → BLOCK）
   - **Freshness 新鲜度**（数据是否最新、是否 STALE）
   - **Uniqueness 唯一性**（主键无重复）
   - **Validity 合法性**（如 `high < low`、`open > high`、`trade_date > snapshot_date` → BLOCK）
   - **Consistency 一致性**（跨表交叉验证；昨日 5300 只今日 4700 只 → ANOMALY 告警）
   - **PIT Safety 时点安全**（如 `ann_date > available_date` → BLOCK，防未来函数）
   （现有 `ops.market_coverage` 是 Completeness 的一部分，保持并扩展）
6. **发布纪律**：基座发版 = 发布新 contract_version + 数据字典更新 + 冻结快照重建校验；
   应用侧锁定版本，升级显式、可回滚
7. **Data SemVer 版本兼容规范**（契约版本变更规则）：
   - **Patch（v1.0.1）**：仅基座内部 Bug 修复或数据重刷，字段集合与口径完全不变，应用无感知
   - **Minor（v1.1.0）**：新增非破坏性字段（如 `ma200`、`volatility_60d`），向前兼容，应用可继续运行
   - **Major（v2.0.0）**：破坏性变更（删字段/改名/改核心指标口径），强制应用升级并完成迁移测试
8. **统一 Run Manifest（Lineage 落地）**：采集/Standard/PIT/Feature/Snapshot/Backtest 每次执行都生成统一
   `run_id`，记录 `job_name / code_commit / config_hash / input_manifest_hash / output_manifest_hash /
   start_time / end_time / rows_read / rows_written / rows_rejected / status / error`。
   这样"2027 年重算 2025-06-17 的 MA60 为何不同"可一路回溯：Snapshot → Feature Run → PIT Run →
   Standard Run → Raw Version → Fetch Batch。（当前各任务各自记录 checkpoint，应统一成一个 run_manifest 模型）

## 10. 大数据量与大事务规避设计（容量规划 + 防坑铁律）

### 10.1 数据量估算（5 年全市场，量化问题严重性）

按 5 年 ≈ 1250 交易日、每日约 5500 只股票估算：

| 表 | 行数 | 形态 | 在 PG 的量级 |
|---|---|---|---|
| `daily_kline`（标准行情） | ~690 万 | 窄表（10 列） | ~100MB |
| `contract.stock_snapshot_daily`（冻结快照宽表） | ~690 万 | **宽表（100+ 列）** | **6~10GB** |
| `feature.price_daily_v2` / `valuation_daily_v1` / `company_financial_v1` | 各 ~690 万 | 中宽表 | 各 ~1~3GB |
| `security_status_daily` / `universe_daily` / `tradeability_daily` | 各 ~690 万 | 窄表 | 各 ~100~300MB |
| 分钟线（股票/指数/ETF） | ~16 亿 | 海量 | 对 PG 不经济，优先 Parquet |
| tick 分笔 | 数十亿 | 海量 | 已 Parquet 冷存（保持） |

结论：**690 万行本身对 PostgreSQL 完全不是问题**（索引合理 + 查询带条件 + VACUUM 正常即可）。
真正的风险是：
1. **宽表快照的高列宽 + 多版本全量复制**（每次修数据生成 v1/v2/v3 → 690 万 → 1400 万 → 2000 万+，存储与扫描成本成倍放大）；
2. **分钟/tick 高频数据规模快速膨胀**（十几亿~数百亿行，PG 技术上能存，但对个人系统不经济，优先列存）。
前者靠分区 + 避免全表扫描 + 控制多版本，后者靠列存外置。

### 10.2 写入侧防大事务（六条铁律）

1. **可配置 chunk 切分**：大任务按「日期窗口 + 股票代码批次」双重切分，chunk 大小**做成配置而非写死**——
   `date_window_days` / `code_batch_size` / `max_rows_per_tx`，不同任务成本不同（日线可月×500 只，复杂 Feature 月×50 只）。
   铁律是"**必须有可配置 chunk，且在 chunk 边界 commit/checkpoint**"，不是"必须 50 只一组"。
   （现状：`tushare_phase2_standard` 按 `_month_windows`、`tushare_phase2_features` 按 `FEATURE_CODE_BATCH_SIZE`——保持并统一成框架）
2. **小事务 + 独立提交**：每批一个事务，写完即 commit，禁止"整表重算一个事务"。长事务会锁死 VACUUM、放大 WAL、阻塞读。
3. **checkpoint / 断点续传**：进度表（如 `ops.foundation_rebuild_checkpoint`，已有）+ 幂等键，失败从断点重跑而非从头。
4. **单并发 + 排他锁**：同表同区间禁止并发写。现状 `build_snapshots_batch` 已有 `_acquire_snapshot_batch_lock`，推广到所有重建任务。
5. **重建模式按场景二选一，勿一刀切**：
   - **增量更新**：同一 business key 少量变化 → `ON CONFLICT DO UPDATE`（幂等 upsert）
   - **大范围确定性重建**：`rebuild_universe` 等整月/整区重建 → 优先 **staging 表 → 建索引 → attach/swap**（或 `DELETE 分区 + COPY`），比几百万次 upsert 更快、WAL 更省
   （注：upsert 并非免费——要查唯一索引 + 判断冲突 + 更新 tuple + 产生 dead tuple）
6. **大事务内禁止全局扫描与重聚合**：`build_snapshots_batch` 里 `_input_stats`（line 1340）在事务内循环全局统计，是大事务 + 大查询叠加，必须移出事务（事务前算好 / 事务外算质量报告）。
   （注：与当前批次规模绑定的轻量校验，如 `SELECT COUNT(*) FROM 当前 staging 小批次`，放事务内无害；禁止的是全局扫描 / 复杂聚合 / 循环统计）

### 10.3 查询侧防大查询（四条）

1. **分区裁剪**：快照/feature 大表按 `trade_date` 分区（§3.1），查询自动裁剪到单日/单月。
2. **索引 + 覆盖索引**：高频查询路径（`ts_code + trade_date`、`snapshot_id + research_date`）建复合索引。
3. **禁止启动时全表 COUNT/MAX/GROUP BY**（agent.md 已记录 16GB 表统计导致宿主机失响的教训）——固化为铁律：统计一律用基线 Manifest / 预聚合 / 近似统计。
4. **超时熔断**：`statement_timeout`（如 60s）、`idle_in_transaction_timeout`、`lock_timeout` 全局设置，长查询/长事务自动打断而非拖垮库。
5. **应用级查询纪律**（单靠 PG 配置不够）：禁止无 `WHERE` 导出大表、禁止默认 `SELECT *`、默认分页、默认日期窗口。

### 10.4 存储分层（日频留 PG，高频外置）

1. **日频数据（行情/Feature/快照）长期留 PG，至少 5~10 年，不要过早归档**：你的 Feature 大量依赖
   5 年窗口（PE 5 年分位、5 年 ROE、52 周），若 PG 只留 2 年，每天重建 `pe_pct_5y` 就要跨 PG+Parquet
   读，复杂度上升。日频 ~690 万行 × 几表并不大，机器成本远小于工程维护成本。
2. **高频历史数据（分钟/tick）列存外置**：分钟线、tick 的历史分析数据原则上不进核心 PG——优先 Parquet
   列存（项目已有 tick 按日 Parquet 先例），PG 仅保存元数据/索引/任务状态。
3. **快照宽表分析走列存（可选）**：`stock_snapshot_daily` 的大规模分析/回测读取可走 §4.6 的 Parquet
   通道（Polars/DuckDB 列扫），但 PG 仍保留全量日频数据作为权威源。

### 10.5 追加式 + 物化隔离（架构模式）

- Raw 只追加（已有）。
- **冻结快照 = 不可变物化**：计算任务写 staging → 校验 → 原子切换 FROZEN，应用永远读"已冻结"版本，读写互不干扰（现状快照 FROZEN 后触发器禁止改，已具备，保持）。
- 后台重建与在线服务隔离：基座计算任务独立子进程（pipeline 已做），不与应用查询抢锁。

> **Snapshot 演进方向（暂不实施）**：Snapshot 的"不变性"不等于"必须物理复制一整份数据"。
> 长期可改为"Snapshot Manifest + Dataset/Feature Version + Partition Reference"——快照只存
> `snapshot_id / asof_date / feature_version / pit_version / source_manifest_hash / contract_version`，
> 实际数据读 Feature/Mart 的不可变分区，避免每个 Snapshot 版本都全量复制一份 690 万行宽表。
> 个人系统第一阶段继续物理复制即可，但要知道"不变性"与"物理复制"是两个概念。

### 10.7 架构纪律总结（五条）

```text
A. 存储分层：日频结构化事实/Feature → PostgreSQL；分钟/tick 历史分析 → Parquet；
             任务/版本/血缘/目录 → PostgreSQL

B. 写入纪律：Chunk → Commit → Checkpoint；禁止超大单事务

C. 重建纪律：增量 → UPSERT；全量/大范围 → Staging → Validate → Atomic Publish

D. 查询纪律：Partition Pruning + 索引 + Timeout + 禁止无界全表扫描 + 应用级分页/日期窗口

E. Snapshot纪律：FROZEN 永不修改；数据修正 → 新版本；分析型大快照可导出 Parquet
```

## 11. 容灾与备份（Disaster Recovery / Backup Policy）

长期运行必须考虑：数据库/磁盘损坏、误删、Parquet 损坏。**Raw 是最宝贵的资产**。第一版无需企业级高可用，但至少：

| 资产 | 备份策略 | 验证 |
|---|---|---|
| PostgreSQL（raw/std/pit/feature/contract/ops） | 定期 `pg_dump`（每日/每周）+ WAL 归档 | **定期做 restore 演练，验证能恢复** |
| Raw 原始表 | 第二份异地/独立介质备份（最宝贵） | 校验 `payload_hash` 一致性 |
| Parquet（分钟/tick） | 文件 checksum + 目录清单 | 定期抽验 checksum |
| Snapshot / Dataset / Manifest | 依赖 PG 备份 + manifest_hash 校验 | 恢复后校验 manifest_hash 不变 |

**铁律：备份不是"有文件就算完成"，必须定期验证能 restore。** 第一阶段用简单脚本 + 定时任务即可，不必上企业级 HA。
