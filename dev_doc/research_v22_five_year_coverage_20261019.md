## 范围、方法与安全边界

使用当前项目只读数据访问 Kernel / Repository，限定数据库身份为 `ashares` / `ashares_app`，核对 `transaction_read_only=on` 且角色不是 superuser，并配置语句、锁和空闲事务超时。查询采用月度/报告期分区；生产端未运行迁移、DML、Release 创建、Snapshot 物化或 Dataset 生命周期操作。只读审计连接校验测试：`tests/test_read_only_audit_kernel.py`，**4 passed**。

曾有一条全区间 PIT 汇总超过预设的执行时限并回滚；随后补上审计连接服务端超时并改用半年度/月度查询，未重复运行该无界聚合。完整 Release Gate 以及证券级公司行为总收益标签均未运行。报告中明确区分“源码/数据库结构已查”“分区统计已查”“未执行的完整验收”。

## 7. 批次建设计划与首批日期

不建议立刻开始五年生产 Snapshot 写入。下列是通过前置门禁后的可恢复计划，不是本次已执行动作：

1. **准备批次（只读/隔离）**：解释 `600699.SH`；追踪 warmup PIT 缺时间戳和 2021-06 Feature 差异；确认生产需要的 v2.2 migration 与 Factor lineage 任务版本。全程保留旧 Release/FROZEN。
2. **首批隔离试建**：选择 `2023-09-12` 至 `2023-10-20` 的 23 个信号日，准备后续 60 个交易日标签尾部至 `2024-01-15`。此前报告核对这段为 83 个连续交易日，适合检验 Snapshot、行情、公司行为、来源哈希和标签；日期较早且完整标签尾部已存在。使用新唯一基线，在 `ashares_test` 中走完链路，不触碰生产。
3. **首批生产发布（单独授权后）**：只有隔离试建、来源质量和 Release Gate 全过，才选择生产中的一小段日期，通过受控 Release/Feature/Snapshot 工作流发布；每月一个不可变批次，身份绑定 Schema、基线 cutoff、质量报告和 source manifest。
4. **向五年扩展**：按信号月恢复运行；每批记录输入/输出行数、哈希、有效因子率、拒绝原因、交易日覆盖及可恢复 checkpoint。出现失败只重跑未完成批次，严禁 truncate 或覆盖旧 FROZEN。
5. **标签与 Alpha 研究**：Snapshot/Dataset 全部完成后，使用执行行情和一致的公司行为/复权口径构造标签；把 2026-08 末端成熟性按证券级标签状态报告，随后才做 Rank IC、分组与稳定性分析。

## 对四个决策问题的回答

1. **现有数据够不够构建五年 v2.2？** 有相当充分的 Raw/Standard/价格与历史 PIT 基础，足以启动受控的分批重算；**当前还不足以直接构建并验收正式五年 FROZEN Dataset**，因为 v2.2 Schema、因子来源 lineage、PIT 时间证据、早期 Feature 覆盖及 Release 公司行为门禁仍阻断。
2. **哪些缺口必须补采，哪些只需重算？** D/A 独立 Feature 是 migration/物化缺口，优先不采；三个财务因子已有很多数值，需按新版质量 lineage 重算/重物化；warmup 时间戳先做 PIT 来源核查，无法证明才针对性补采或缩小范围；行情和公司行为缺口按逐证券/事件证据处理。当前没有证据支持五年全量补采。
3. **新 Foundation Release 当前能否创建？** **不具备条件。** 所有旧 Release 均 superseded，现行公司行为门禁有 1 条全库 UNRESOLVED；新版质量/数据身份也尚未构建。完整 Release Gate 本次未运行。
4. **首批真实 v2.2 Snapshot 选哪段日期？** 先在隔离库用 `2023-09-12`–`2023-10-20` 的 23 个信号日及至 `2024-01-15` 的 60 日执行尾部做 E2E。理由是已有日历和真实行情覆盖，窗口完整、可重现，适合先验证新字段/lineage 与冻结读取；它不代表已经选定或创建生产 Release。
